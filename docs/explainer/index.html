A field guide to the code · jsnelgro/atdrive

How ATDrive works

ATDrive is a Dropbox-style drive that lives inside your own atproto account. Your files sit in a private space on your PDS. On a Mac they show up in Finder; on Linux a normal folder stays in sync with them. This guide follows the code from your desktop down to the wire and back.

That one address is your whole drive. Everything below happens inside it.

Package.swift

One core, three ways in

Everything is one SwiftPM package with no Xcode project. A single library does the real work, and the things you click or type are thin layers on top of it.

Three ways in

On a Mac, the drive appears in Finder through a File Provider extension, with a small menu-bar app that signs you in. On Linux, atdrive sync keeps an ordinary folder, ~/atdrive, mirrored with the drive. Everywhere, the atdrive command line lists, uploads and downloads directly.

One core

All three link the same library, ATDriveCore. It has no AppKit and no UI, so it builds on Linux as well as macOS.

Identity lookup, OAuth, the HTTP client, the record model, the tree, uploads, the conflict rules and the folder sync all live here. The front ends mostly translate between their world (Finder callbacks, a folder on disk, command-line flags) and calls into the core.

One place in your account

The core talks to one server: your PDS (personal data server), the same server that holds your Bluesky posts. Your drive is a single private space there. Files and folders are records in it; file contents are blobs.

Nothing hardcoded

ATDrive doesn't know where your PDS is ahead of time. It starts from your handle and looks the server up, the same way every atproto app does. Chapter 3 walks through it.

Identity.swift · OAuth.swift · DPoP.swift · LoopbackServer.swift · Session.swift

Finding your server and signing in

atdrive login alice.example.com, or the menu-bar app's sign-in, runs the full atproto OAuth flow. You approve ATDrive on your own PDS's page in the browser, so ATDrive never sees your password.

1 · Handle → DID → PDS

First: who are you, and where is your data? ATDrive fetches https://alice.example.com/.well-known/atproto-did, falling back to com.atproto.identity.resolveHandle on a public server, and gets a DID like did:plc:….

Then it downloads the DID document from plc.directory (or /.well-known/did.json for a did:web) and reads the service tagged #atproto_pds. That URL is your PDS. Both lookup servers can be changed with environment variables.

2 · Find the authorization server

The PDS's /.well-known/oauth-protected-resource names the server that handles sign-in (usually the PDS itself), and that server's /.well-known/oauth-authorization-server lists its endpoints. ATDrive checks that the issuer it was sent to is the one that answered.

3 · Make secrets, push the request

ATDrive makes three things that never leave the machine: a fresh P-256 DPoP key, a PKCE verifier, and a random state. It sends a pushed authorization request (PAR) with the verifier's hash, the scope and a DPoP proof, and gets back a short request_uri.

The scope it asks for:

atproto space:*?collection=me.jsnelgro.atdrive.node&manage=create blob:*/*

space:* is broader than ATDrive needs. Naming its own space type would make the PDS look up the published lexicon for the consent screen, and that lexicon isn't published yet (PLAN.md has the steps).

4 · You approve in the browser

ATDrive opens your PDS's authorize page and you sign in there. ATDrive is a public native client with no website of its own, so its client ID is atproto's loopback form, http://localhost?scope=…, which needs no hosted metadata.

5 · The browser comes back to 127.0.0.1

LoopbackServer listens on a random local port and catches the redirect, ?code=…&state=…&iss=….

Over SSH the browser is on another device, so that page fails to load. You paste its address into the terminal instead, and whichever arrives first wins. Pasting is safe: the code is useless without this process's PKCE verifier and DPoP key.

6 · Swap the code for tokens

The code, the PKCE verifier and a DPoP proof go to the token endpoint. Back come an access token and a refresh token, both bound to the DPoP key.

ATDrive checks that the token's sub is the DID it resolved in step 1, then saves the tokens and the key to ~/.config/atdrive/session.json, readable only by you. The Mac app saves them in its App Group container instead.

7 · Every request carries a proof

Each call sends Authorization: DPoP <token> plus a DPoP header: a fresh JWT signed with the key, naming the method, the URL, the time and a hash of the token. A stolen token is useless on its own.

When the server asks for a new nonce (use_dpop_nonce), the request is signed again and retried once. When the token expires, the SessionManager actor refreshes it once, even if many requests notice at the same moment. Sessions end after two weeks; then you sign in again.

XRPC.swift · Spaces.swift · HTTP.swift

Every request ATDrive sends

atproto's HTTP API is called XRPC: GET for queries, POST for procedures, and method names that are NSIDs. Outside of sign-in, ATDrive uses eleven methods. The six from the spaces alpha all live in Spaces.swift, because that API changes weekly and this keeps a protocol change to one file.

MethodKindWhat ATDrive uses it for
com.atproto.space.getLatestCommitquery"Has anything changed?" Returns the space's revision. Asked every 30 seconds.
com.atproto.space.listRecordsqueryThe whole drive, 1,000 records a page. A record that won't decode is skipped, so one odd record can't break the listing.
com.atproto.space.putRecordprocedureCreate, edit, rename or move one file or folder.
com.atproto.space.applyWritesprocedureDelete records, 200 per request (the server's limit), deepest first.
com.atproto.space.createSpaceprocedureCreate the drive with the personal-space policy, the first time a write gets SpaceNotFound.
com.atproto.space.getBlobqueryDownload one chunk of a file.
com.atproto.repo.uploadBlobprocedureUpload one 4 MiB chunk. It stays private until a record in the space references it.
com.atproto.identity.resolveHandlequeryFind a DID when the handle has no /.well-known/atproto-did.
com.atproto.server.createSession
com.atproto.server.refreshSession
com.atproto.server.deleteSession		procedureApp-password sign-in (atdrive login --app-password), for scripts and tests only.

When a request fails

All of these go through one method, XRPCClient.send. It signs the request through the SessionManager, then decides what to do with a failure. Writes are not retried after a network error, because the client can't tell whether they landed.

Below it sits HTTPTransport, a one-method protocol. It's the only code that touches the network, which is why the tests can swap in an in-memory PDS.

  • networkon a GETRetry up to 3 more times, after 0.5, 1 and 2 seconds.
  • 401use_dpop_nonceSign again with the server's new nonce and retry once.
  • 401expired tokenRefresh the token (one refresh shared by every waiting request), then retry.
  • 429rate limitedWait until ratelimit-reset, at most 60 seconds, up to 5 times.
  • 5xxon a GETBack off and retry, up to 3 more times.
  • refreshrejectedStop with "your session has ended; sign in again".

Records.swift · DriveTree.swift · TID.swift · Lexicon.swift · lexicons/

Files and folders are records

A space is a private collection of records. ATDrive defines two lexicons: the space type me.jsnelgro.atdrive.drive, and the record type me.jsnelgro.atdrive.node.

One space

Your drive is one space, under the personalspace policy: only your account can read or write it. The first write creates it.

Spaces control who can access data. They don't encrypt it, so whoever runs your PDS can read your files.

One record per item

Every file and folder on the left is one node record on the right, whatever its depth. No folder listing is stored anywhere. Each time the drive is listed, DriveTree rebuilds the tree from the flat list of records.

Parents by ID

A record stores its name and its parent: the record key of the folder it's in, or nothing at the top. Paths like /Photos/cat.jpg are worked out in memory by following parents upward.

A move is one write

Drag Photos into Archive. In the tree a whole branch moves, but on the PDS only one record changes: Photos' parent. Renaming works the same way. It doesn't matter how much the folder holds.

Keys are TIDs

Record keys are TIDs: 13 characters of sortable base32, 11 for the time in microseconds and 2 for a random clock ID. ATDrive's generator never repeats or goes backwards within a process.

A key never changes, through any rename or move, so it is the item's identity everywhere: in the Mac's File Provider and in the folder sync's state file.

Drive.swift · Encoding.swift

File contents are chunked blobs

The record says what a file is. Its bytes live beside it as blobs, and ATDrive checks every one of them on the way up and on the way down.

1 · Split into 4 MiB chunks

Drive.upload reads the file 4 MiB at a time and feeds each chunk into a running SHA-256 of the whole file. This 9 MiB PDF becomes three chunks: 4, 4 and 1 MiB.

2 · Upload each chunk, then check it

Each chunk goes up with com.atproto.repo.uploadBlob, and the PDS answers with the chunk's CID, a content identifier. ATDrive computes the CID itself and stops if the two differ.

A blob CID is just a hash with a short header, so it's cheap to compute locally:

"b" + base32( 01 55 12 20 digest )
              │  │  │  │  └ SHA-256 of the chunk
              │  │  │  └ length: 32 bytes
              │  │  └ hash: sha2-256
              │  └ codec: raw bytes
              └ CID version 1
→ bafkreiclrq6vxxygalonwcrgqd4pd7…
3 · Then write the record

The record lists the chunks in order, with the size and the whole-file SHA-256, and goes up with putRecord. Uploaded blobs stay private until a record in the space references them. If none ever does, the PDS deletes them.

If the space doesn't exist yet, putRecord fails with SpaceNotFound. ATDrive creates the space and tries once more. That's the only place a drive gets created.

4 · Downloads check everything

Each chunk from com.atproto.space.getBlob must match its CID, and the whole file must match its size and SHA-256. The bytes go to a hidden .2026.pdf.atdrive-partial file, which is renamed into place only when every check passes. The file gets its original modification time back.

A file's chunk list has to fit in one record (1 MiB at most), which caps a single file at about 30 GB.

Noticing changes: one cheap question

Listing every record is the expensive part, so nothing lists the drive on a timer. Every 30 seconds the folder sync and the Mac ask getLatestCommit for the space's revision, a TID that moves on every write. Only when it has moved do they list everything again.

In atdrive sync

A change in the folder wakes the loop within about a second (inotify on Linux). That pass asks the drive first only if the folder now differs from the last agreed state; otherwise the drive waits for its regular 30-second check.

On the Mac

The revision doubles as the File Provider's sync anchor. "What changed since revision X?" is answered by comparing two cached trees (chapter 10).

The cost

This is polling, not push. A change made on another device shows up within about 30 seconds.

Sync/FolderSync.swift · Sync/SyncPlan.swift · Sync/SyncState.swift · Sync/LocalFiles.swift

A sync pass, step by step

atdrive sync keeps ~/atdrive and the drive the same in both directions. It works in passes, and each pass compares three versions of every item. Two versions can't tell "deleted here" from "new on the drive". The third one, the last state both sides agreed on, can.

  • Last agreed: .atdrive/state.json
  • This folder, now
  • The drive, now
1 · Look at the folder, cheaply

FolderScan lists everything with lstat only. A file is read and hashed only when its size, times or inode changed since the last pass. todo.txt didn't change, so its saved hash is reused. plan.md did, so it's hashed: it was edited.

Files written in the last 2 seconds wait for the next pass, since they may still be being written.

2 · Give every local item a node ID

Items still at their old path keep their ID. Then renames and moves are found by inode: kitty.jpg is the old cat.jpg. Files copied and deleted (across disks, say) are found by hash.

Anything left is new and gets a temporary ID, +ideas.txt. Record keys never contain +, so the two can't collide.

3 · Ask the drive

One getLatestCommit. The revision moved, so the pass lists the drive. Another device edited plan.md and deleted todo.txt, and receipt.pdf is new.

4 · Merge, item by item

SyncPlan takes each ID and asks ConflictRules (next chapter).

Edited on both sides, differently: the drive's version keeps the name, and yours becomes plan (conflicted copy 2026-11-09 1432).md. Renamed only here: the rename goes to the drive. Deleted on the drive and untouched here: deleted here. New on one side: copied to the other.

The plan is a pure function of the three views. It touches neither the disk nor the network, which makes it easy to test.

5 · Apply it in three phases

① The folder. Moves go through .atdrive/staging, with a journal so a killed pass can put things back. A file is deleted only if its lstat hasn't changed since the scan.

② The drive. New folders, uploads and moves, then deletes, deepest first.

③ Downloads. Into .atdrive/downloads, then renamed into place. For the conflict, your plan.md is renamed to the copy first, then the drive's version arrives under the original name.

6 · Save only what finished

The new agreed state goes to state.json, but only for items that got through every phase. Temporary IDs are replaced by the record keys the drive just assigned.

Anything interrupted keeps its old entry, so the next pass picks up where this one stopped, and an interrupted conflict doesn't produce two copies.

1 / 6Scan

The loop around it

  • inotify wakes a pass about a second after the folder changes; the drive is checked every 30 seconds (--interval).
  • After an error it waits 15 seconds, doubling up to 5 minutes.
  • When the session ends it waits for atdrive login, then carries on.
  • --install writes a systemd user service. Exit status 78 marks problems a restart won't fix, so systemd doesn't retry them.

Guards

  • If the folder or .atdrive disappears (an unmounted disk, say), syncing stops instead of deleting the drive.
  • A folder synced with one account refuses another.
  • A lock file lets only one sync run per folder.
  • Nothing local is overwritten or deleted if it changed after the scan. It waits for the next pass.

First sync, and what's skipped

  • A first sync is a merge from an empty state: matching files and folders pair up, and nothing is deleted.
  • Not synced: symlinks and special files, .DS_Store, Thumbs.db, and editor swap and lock files (Vim, Emacs, LibreOffice, Office).

ConflictRules.swift · ConflictName.swift

Who wins when both sides changed

The rules live in one 71-line file. Both the Linux folder sync and the Mac extension call it, so a change ends up the same whichever device made it. Pick what happened to /docs/notes.txt on each side since the last sync.

The three functions behind the matrix

// base = last agreed, local = this device, remote = the drive
static func contents(base: String?, local: String?, remote: String?) -> Contents {
    if local == remote || local == base { return .remote }
    return remote == base ? .local : .conflict
}

static func location<L: Equatable>(base: L, local: L, remote: L) -> L {
    local == base || remote != base ? remote : local
}

static func deleteStands(base: String?, other: String?) -> Bool { base == other }

Contents are compared by SHA-256, so an identical edit on both sides counts as no conflict. When both sides moved a file, the drive's move wins because it's the one other devices already see.

Two rules that span several items

A deleted folder keeps what changed inside it. You delete /trip here while, on another device, a photo was added to it:

Here

trip/a.jpgb.jpg

The drive

trip/a.jpgb.jpgnew.jpg

Result

trip/new.jpg

Two different things, one name: the one that arrives second is renamed name (conflicted copy 2026-11-09 1432). Two identical things (two folders, or two files with the same contents) become one.

Sources/Mac · scripts/build-app.sh

On the Mac, Finder does the syncing

On macOS, ATDrive doesn't keep a folder in sync itself. It plugs into Apple's File Provider framework, the one iCloud Drive and Dropbox use: macOS keeps the local copies and calls the extension whenever data needs to move.

Sign in, add the drive

The menu-bar app runs the same OAuth sign-in and saves the session in an App Group container that it shares with the extension. Then it registers a File Provider domain, and ATDrive appears in Finder's sidebar under Locations.

The app is small on purpose. Every transfer happens in the extension.

A nudge every 30 seconds

The app calls signalEnumerator(for: .workingSet). macOS then asks the extension what changed since the last sync anchor it handed out.

The anchor is the revision

DriveIndex, an actor, checks getLatestCommit. If the revision moved, it lists the drive and keeps the tree, remembering the last 16 by revision.

To answer "what changed since revision X", the enumerator diffs the tree at X against the tree now and reports updates and deletions. If X is too old to remember (the extension restarted), it reports the anchor as expired and macOS lists everything again.

Files download when you open them

Finder shows placeholders. Opening one makes macOS call fetchContents, which runs the same verified Drive.download into a temporary file and hands it over. Remove Download frees the space again.

Changes from Finder, same rules

Saving, dragging in, renaming or deleting arrives as createItem, modifyItem or deleteItem, along with the item version macOS based the change on.

ATDrive puts the SHA-256 in that version's content half and the folder and name in its metadata half. So it can hand ConflictRules the same base, local and remote it uses on Linux.

A build quirk worth knowing

An app extension's executable must not have a main: the extension runtime calls it if it exists, and a main that starts the extension recurses until it crashes. SwiftPM always gives executables one.

So the extension is built as a dynamic library, and build-app.sh links a code-free executable around it with -e _NSExtensionMain, as Xcode does. The script also fills in the Info.plists and entitlements and signs everything. Adding the drive to Finder needs an Apple Development certificate.

Tests/ATDriveCoreTests · .github/workflows/ci.yml

Tests, and what it can't do yet

How it's tested

70 tests, written with Swift Testing. Most run against FakePDS, an in-memory HTTPTransport that implements the few endpoints the drive uses. It can corrupt downloads, fail chosen calls with a 500, and page results two records at a time.

FolderSyncTests (30 tests) syncs real temporary folders: first-sync merges, edits, moves and deletes in both directions, conflicts, interrupted passes and the inotify watcher. ConflictRulesAgreeWithSyncTests checks that the folder sync keeps exactly what keptWhenDeleting keeps.

Two suites run only when you ask: OAuthLiveTests starts a real sign-in up to the approval page (ATDRIVE_LIVE_HANDLE), and LiveTests does a full upload and download with an app password. CI runs everything on Linux and macOS, and assembles the Mac app unsigned.

scripts/test.sh                 # unit tests, no network
scripts/test.sh --filter SyncPlan
scripts/build.sh                # build/atdrive
scripts/run-app.sh              # macOS: build, install, launch

Known limits

  • No compare-and-swap. The spaces alpha can't make a write conditional, so put, mv and rm are last-write-wins, and an edit made elsewhere in the second before a sync uploads can still be overwritten.
  • Polling. Changes from elsewhere take up to 30 seconds.
  • Whole files. atdrive sync re-uploads a whole file even when a little of it changed, and transfers run one at a time.
  • Not encrypted. Spaces limit who can read; your PDS operator still can.
  • Two-week sessions for apps without a backend, then sign in again.
  • Broad scope (space:*) until the lexicons are published.
  • No trash, no symlinks, and one drive per account.
